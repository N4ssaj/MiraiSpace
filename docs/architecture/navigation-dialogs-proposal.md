# Навигация, DI и регионы диалогов

Обновлено 2026-09-07 по последнему обсуждению. Принятые решения ниже отделены от эскизов сигнатур. Старый экспериментальный код ещё не приведён к этой модели.

## Принятые решения

- Использовать встроенную навигацию Avalonia: NavigationPage и ContentPage.
- Для первой реализации — обычный стек и переход назад. Пользователь явно выбрал этот вариант; браузерного Forward не будет.
- CanGoBack и CanGoForward не нужны в публичном INavigationService приложения.
- Одна логическая панель/плавающее окно имеет свою DI scope и свою навигацию с одной текущей страницей.
- Диалоги получают ViewModel, созданную с участием DI, и встраиваются в выбранный регион страницы или конкретного компонента.
- Title не является обязательной частью контракта диалога. URL к диалогам не относятся.
- Повторную инициализацию одного экземпляра пока не вводим. Для обновления данных — отдельный метод конкретной VM, когда появится сценарий.
- Autofac добавляем только при реальной необходимости.
- Демо должно проверять обязательные параметры страницы, DI и региональное отображение диалогов.

## Навигация на Avalonia

В проекте уже Avalonia 12.1.1, .NET 10 и C# 14. Наличие NavigationPage, ContentPage и INavigation проверено по установленному Avalonia.Controls.xml, не только по актуальному сайту.

NavigationPage хранит стек Page и выполняет PushAsync, PopAsync и переходы с анимацией. Поэтому собственный список URL с индексом истории больше не должен быть вторым владельцем стека.

Наш слой сохраняет только прикладные обязанности: разобрать URL, проверить обязательные параметры/доступ, получить VM через DI, подготовить её и сопоставить с View. UI-адаптер передаёт подготовленную ContentPage в NavigationPage.

```csharp
// Эскиз прикладного контракта, сигнатуры ещё обсуждаем.
public interface INavigationService
{
    NavigationEntry? Current { get; }

    Task<NavigationResult> NavigateAsync(
        string address,
        CancellationToken cancellationToken = default);

    Task<NavigationResult> GoBackAsync(
        CancellationToken cancellationToken = default);
}
```

Уведомление об изменении Current необходимо для меню; точную форму наблюдения ещё согласуем. Структура меню не строится автоматически из маршрутов. Контейнер сам компонует и фильтрует детей.

CanGoBack имеется у самого NavigationPage; представление кнопки назад может использовать состояние контрола. Переносить это свойство в прикладной контракт ради UI не требуется. Вызов Back на корневой странице не является исключительной ситуацией.

ContentPage — представление, ReactivePage — ViewModel. Логику загрузки, разрешения на уход и диалогов оставляем в VM/сервисах. Документационные примеры с new DetailsPage и бизнес-логикой в OnNavigatingFrom не копируем в Views; адаптер/behavior связывает события контрола с прикладным API.

Существенные особенности для реализации:

- Возврат к странице, оставшейся в нативном стеке, не вызывает повторную InitializeAsync.
- Навигационное событие NavigatedFrom не означает уничтожение страницы: она может оставаться в стеке.
- Ресурсы удалённой страницы освобождаются после её фактического удаления и завершения перехода.
- В установленной версии Page.Navigating поддерживает ожидаемые асинхронные обработчики. Это позволяет адаптеру дождаться решения VM без async void во View.
- PushAsync/PopAsync не принимают наш CancellationToken. Отмену подготовки нельзя выдавать за гарантированную отмену уже начавшейся анимации.
- При занятом NavigationPage некоторые методы возвращаются без изменения стека. Координатор должен учитывать это; завершение Task само по себе не доказывает успешный переход.
- Кнопка назад, системный Back и палитра должны проходить согласованный путь координации и обновления активного назначения.
- Нативный стек содержит живые страницы. Сохранение состояния между запусками остаётся отдельной темой настроек.

## Область жизни панели

Создание логической панели создаёт одну scope. Из неё получают навигацию, сервис диалогов, модели страницы и необходимые им зависимости. Закрытие панели завершает принадлежащие ей операции и освобождает scope асинхронно.

Предлагаемая схема:

```text
Generic Host
├── scope панели A
│   ├── навигация A → NavigationPage A
│   ├── сервис диалогов A
│   ├── регион страницы A
│   └── регион компонента «Редактор A»
└── scope панели B
    ├── навигация B → NavigationPage B
    ├── сервис диалогов B
    └── собственные регионы страницы и компонентов
```

Привязать scope лучше к логической панели, а не к временной визуальной оболочке DocumentPane/FloatGroup. Перемещение панели или переподключение её к visual tree не должно пересоздавать навигацию либо освобождать рабочую scope.

Регион сам по себе не требует отдельной DI scope. У стандартного Microsoft DI области не наследуют scoped-экземпляры друг друга: создание новой scope «для диалога» иначе даст ему другую навигацию. Для первой модели VM диалога использует зависимости своей панели. Если понадобится настоящее вложенное время жизни с наследованием сервисов — тогда оцениваем Autofac.

## Диалоги: ViewModel из DI

Ручное создание зависимой VM вызывающим кодом исключаем. Для уже полученной через DI модели вызов выглядит так:

```csharp
var result = await _dialogs.ShowAsync(
    _renameDialog,
    region: _editorRegion,
    cancellationToken: cancellationToken);
```

_renameDialog получена через DI; _editorRegion идентифицирует регион конкретного экземпляра редактора. Для нового диалога с параметрами на каждое открытие подходит типизированная DI-фабрика:

```csharp
var dialog = _renameDialogFactory.Create();
await dialog.InitializeAsync(documentId, cancellationToken);

var result = await _dialogs.ShowAsync(
    dialog,
    region: _pageRegion,
    cancellationToken: cancellationToken);
```

Фабрика создаёт свежую VM с зависимостями панели. Самостоятельный GetRequiredService в каждой вызывающей VM не нужен. Кто освобождает созданную VM, определяется владельцем фабрики/операции; сервис показа не должен произвольно Dispose экземпляр, принадлежащий вызывающему коду.

Предлагаемая форма сервиса:

```csharp
public interface IDialogService
{
    Task<DialogResult<TResult>> ShowAsync<TResult>(
        IDialogViewModel<TResult> viewModel,
        DialogRegion? region = null,
        CancellationToken cancellationToken = default);

    Task CloseAsync<TResult>(
        IDialogViewModel<TResult> viewModel,
        DialogResult<TResult> result);
}
```

IDialogViewModel<TResult> здесь — предложенная типовая связь VM с результатом; это ещё не утверждённый интерфейс. В нём не нужны Title, TaskCompletionSource и Completion. Сессия и ожидание принадлежат одному вызову ShowAsync. Подтверждающая команда VM может передать this и типизированный результат в CloseAsync; Cancel тоже является результатом завершения показа. Конкретный API закрытия ещё обсуждаем.

Не вводим обязательный ReactiveDialog: модель содержимого можно строить на ReactiveComponent или ином подходящем основании. Заголовок, если нужен, остаётся свойством конкретной VM и её View.

## Регионы страницы и компонентов

Регион — логическая область отображения со своим владельцем и временем жизни. View содержит соответствующий DialogHost и связывает его с регионом через UI-адаптер/behavior. Решение показать диалог принимает VM.

- Регион страницы перекрывает содержимое страницы.
- Регион компонента перекрывает только этот компонент; остальная страница доступна.
- Два экземпляра одного компонента имеют разные региональные идентификаторы, даже если оба называются Editor.
- Для собственного API предлагаю ссылку/токен DialogRegion, а не глобальную строку. UI-адаптер при необходимости преобразует её в Identifier библиотеки.
- Если регион не указан, предлагаемый вариант по умолчанию — регион текущей страницы в scope панели.
- Незарегистрированный либо уже удалённый регион не должен молча заменяться регионом всей страницы.
- Удаление компонента или закрытие панели завершает принадлежащие региону диалоги и снимает подписки.
- Диалоги независимых компонентов могут быть открыты одновременно.
- Когда открывается диалог поверх всей страницы, вложенные регионы под ним не должны получать ввод.
- Очередь/стек повторных диалогов в одном регионе ещё не выбраны; не добавляем произвольную политику без сценария.

DialogHost.Avalonia уже имеет встраивание над конкретным содержимым, DialogContent/шаблоны, Identifier, DialogSession и результат закрытия. Поэтому первый кандидат — небольшой адаптер поверх готового контрола. Копирование/форк оправдано конкретным ограничением, которое нельзя решить шаблоном или адаптером; сейчас такое ограничение не установлено.

MessageBox можно сделать готовым содержимым для того же регионального хоста. Обычные диалоги не должны автоматически превращаться в отдельные Window. Нативные системные окна при необходимости остаются отдельной явно выбранной возможностью. PushModalAsync у NavigationPage сам по себе не заменяет регионы компонентов.

## Демо для следующей базовой реализации

Текущий /workspace/pages/{id} уже формально имеет параметр, но показывает ту же универсальную VM и фактически подменяет заголовок. Этого недостаточно для проверки архитектуры.

Предлагаемый связный сценарий:

1. Список документов → конкретный документ по /documents/{documentId}.
2. DocumentPageViewModel требует типизированные параметры с Guid и получает репозиторий через DI.
3. Репозиторий возвращает различимые демодокументы; обязательный параметр влияет на реальную загрузку.
4. Нет параметра, неверный Guid и корректный, но отсутствующий документ — разные ожидаемые случаи.
5. Внутри документа есть компонент редактора с собственным регионом.
6. Переименование открывается в регионе редактора; удаление документа — в регионе страницы.
7. Обе VM диалогов получают зависимости через DI, возвращают типизированный результат и не создают Window.
8. Back возвращает к странице, оставшейся в NavigationPage; инициализация повторно не вызывается.
9. Позднее тот же сценарий открывается в двух панелях, чтобы проверить независимость scope, навигации и регионов.

## Фактическое состояние кода

- Схема Generic Host восстановлена в предыдущем шаге; палитра существует на старом экспериментальном сервисе.
- В этом обсуждении три object-поля синхронных блокировок заменены на System.Threading.Lock. SemaphoreSlim для асинхронного ожидания сохранён.
- InMemoryEventBus/IEventBus ещё не заменены на MessagePipe.
- AvaloniaDialogService пока создаёт отдельные окна, IDialogRequest<TResult> содержит Title/Completion/Cancel, и есть старые локальные catch в командах. Всё это остаётся известной работой для замены старой реализации.
- NavigationPage, новый параметризованный демосценарий и региональные диалоги описаны здесь, но ещё не внедрены.
- Повторную инициализацию, Autofac и новые библиотеки в этом шаге не добавляли.
